# Ветка — архитектура

## 1. Монорепозиторий

```
.
├── ios/
│   ├── branch.xcodeproj         тонкий app-target: composition root, табы, роутеры
│   ├── branch/
│   └── Packages/VetkaKit/       SPM-пакет, все модули — его таргеты (см. §4)
├── backend/                     один Go-модуль `vetka`
│   ├── cmd/api/                 HTTP + WebSocket
│   ├── cmd/worker/              счётчики, hot_rank, медиа, GC
│   ├── internal/
│   │   ├── httpapi/             chi-роутер, middleware, хендлеры
│   │   ├── auth/ user/ community/ post/ comment/ vote/ feed/ media/ realtime/
│   │   ├── ranking/             «горячее»
│   │   └── platform/            postgres (pgx), redis, s3
│   ├── migrations/              goose
│   └── api/openapi.yaml         контракт API, из него же — DTO для iOS
├── infra/
│   └── docker-compose.yml       postgres, redis (+ S3 и imgproxy с модулем медиа)
└── docs/
```

**chi, а не fiber**: chi — это `net/http`, совместимый со всей экосистемой
(middleware, `coder/websocket`, HTTP/2, `httptest`). Fiber на fasthttp ломает эту
совместимость, а выигрыш в скорости для нас незаметен на фоне БД.
Доступ к БД — **pgx без ORM и кодогенерации**: SQL лежит рядом с кодом, который его
вызывает, и проверяется интеграционными тестами на настоящем Postgres
(`internal/testdb` создаёт отдельную БД на каждый тест). Миграции — **goose**,
отдельной командой `cmd/migrate`.

## 2. Схема БД

Миграция: [`backend/migrations/00001_init.sql`](../backend/migrations/00001_init.sql).

- **`bigint identity` вместо UUID**: индексы меньше, «новое» сортируется по `id`,
  курсор пагинации — одно число.
- **Keyset-пагинация** везде: `(hot_rank, id) < ($rank, $id)`, никаких `OFFSET`.
  Под каждую ленту — свой частичный индекс `WHERE deleted_at IS NULL`; «горячее»
  читается Index Only Scan.
- **Голоса**: строка = текущий голос, снятие = `DELETE`. PK `(user_id, post_id)` —
  под запрос «мои голоса для этих 25 постов». Клиент шлёт желаемое состояние
  (`-1/0/1`), а не toggle, поэтому запрос идемпотентен.
- **Счётчики голосов — через outbox, не триггером.** Голос (`PUT /v1/posts/{id}/vote`)
  пишет строку в `post_votes` и дельту в `vote_deltas` **в одной транзакции**;
  `cmd/worker` раз в секунду забирает дельты пачкой (`FOR UPDATE SKIP LOCKED`),
  суммирует по посту и одним statement'ом обновляет `upvotes/downvotes/hot_rank`
  и карму. Иначе горячий пост упирается в блокировку одной строки. Изначально
  дельты планировались в Redis, но запись в Postgres + Redis не атомарна и при
  сбое счётчик тихо расходится; outbox в той же БД исключает это по построению
  (тест: при любых параллельных голосах счётчики = пересчёт `post_votes`).
  Пропускная способность сброса — ~150k голосов/с на ноутбуке. Ответ на голос
  отдаёт счёт с учётом ещё не применённых дельт; в лентах счёт отстаёт ≤1 с.
  Голос за свой пост двигает счёт, но не карму.
  Счётчики комментариев — синхронным триггером: комментариев на порядки меньше.
- **Комментарии**: список смежности + `root_id` + `depth` (вычисляются триггером).
  Ответ — страница верхнего уровня (keyset по `(score, id)` или `id`) плюс
  дерево под ней одним рекурсивным CTE: на каждом уровне `LATERAL` берёт
  **топ-8 ответов каждого родителя** по индексу `parent_id`, до 5 уровней вниз,
  не больше 400 строк (Postgres вычисляет CTE по уровням и только до `LIMIT`,
  так что лимит срезает самые глубокие ответы). Поэтому показанные ответы —
  всегда префикс отсортированного списка, и заглушка `more` несёт курсор, с
  которого `GET /v1/comments/{id}/replies` продолжит без дублей и пропусков.
  Go раскладывает дерево в плоский список в порядке отрисовки: комментарии с
  абсолютным `depth` и заглушки `more` («ещё N ответов», догружаются на месте)
  и `continue` («продолжить ветку», новый экран). Инвариант, проверяемый
  тестами: показанные ответы + число в заглушке = `reply_count`. Удалённый
  комментарий остаётся надгробием (без текста и автора), ответы под ним живы.
  Тред на 70k комментариев: страница 0.1 мс, дерево 2.8 мс.
  ltree не используем: сортировка его путей лексикографическая (`"100" < "99"`).
- **Медиа** с `width/height/thumbhash` обязательно: ячейка верстается до загрузки
  картинки, без прыжков. Варианты размеров не храним — их отдаёт imgproxy.
- **Сообщества**: подписка (`community_members`) и модерация
  (`community_moderators`) — разные таблицы, модератор может отписаться и остаться
  модератором. Счётчик подписчиков — триггером. Подписка — `PUT`/`DELETE` состояния,
  не toggle. NSFW-сообщества не попадают в «популярные» и поиск (требование App Store
  прятать такой контент по умолчанию). Не больше 3 новых сообществ в сутки на
  пользователя — защита от захвата хороших имён.
- **Посты и ленты**: `GET /v1/feed/all`, `/v1/feed/subscriptions`,
  `/v1/communities/{slug}/posts`, все с `sort=hot|new`. В лентах — превью тела
  (600 символов + `body_truncated`), полный текст — в `GET /v1/posts/{id}`.
  Лента подписок — `LATERAL`: по `limit` постов с каждого сообщества из
  `posts_community_hot_idx`, потом слияние; стоимость растёт с числом подписок,
  а не постов (50 подписок, 200k постов — 2.6 мс). Заголовок поста не редактируется:
  голоса и комментарии давали к нему. Лимит — 10 постов в час (Redis, фиксированное
  окно). В каждом посте — `my_vote` зрителя из того же запроса.
- **Истории** (миграция 00008): посты одного автора, связанные в части.
  Отдельная таблица `stories` и `posts.story_id/story_part`, а не ссылка
  «продолжение поста X»: номер части и оглавление — один проход по индексу
  `(story_id, story_part)`, без обхода цепочки. Новая часть всегда в конец;
  `story_part` только растёт, а читателю номер считается по живым частям, так
  что удаление части не оставляет дыр. Две части, опубликованные разом,
  сериализуются блокировками строк (пост, потом история) — тест на гонку.
  Продолжать можно только свой пост. В каждом посте — `story: {id, part, parts}`
  (LATERAL-подсчёт только для постов из историй), оглавление —
  `GET /v1/posts/{id}/story`.
- **Профиль**: `GET /v1/users/{username}` (+ `/posts`, `/comments` с контекстом
  поста), `GET|PATCH|DELETE /v1/me`, `GET /v1/usernames/{name}/availability` для
  живой проверки при онбординге. Первая смена ника бесплатна (выбор вместо
  выданного `user_xxxxxxxx`), дальше раз в 30 дней; смена только регистра — всегда.
  NSFW-посты и комментарии под ними в чужом профиле не видны. Удаление аккаунта
  (требование App Store): ник освобождается (`deleted_<id>`), входы и сессии
  отзываются, подписки снимаются; посты и комментарии остаются без автора.
  TODO: отзыв токена Apple через REST API при удалении — нужен обмен
  `authorization_code` при входе и ключ `.p8`.
- **Правила сообщества**: `communities.rules jsonb` (миграция 00009) — список
  `{title, body}`, до 15 штук, читаются и меняются только целиком (`PATCH
  /v1/communities/{slug}` с `rules` заменяет весь список). Отдаются только в
  одиночном сообществе (`GET`, ответы PATCH и подписки); в списках поля нет,
  для клиента `rules == nil` значит «не загружено», а не «правил нет».
- **Поиск**: люди — по нику и имени (trigram, `users_display_name_trgm_idx`
  в 00010), посты — по заголовку, одна страница по близости и «горячести»,
  без NSFW. «Популярные запросы» — `search_query_hits (day, query, user_id)`:
  человек считается раз в день, в тренд попадает запрос ≥3 разных людей за
  неделю (один человек тренд не накрутит), анонимные не пишутся; воркер раз
  в час удаляет строки старше окна. Пока данных мало — названия крупных
  сообществ.
- **Курсоры** непрозрачные (base64 JSON), конверт списков — `{items, next_cursor}`.
  Клиент не знает, по чему отсортирован список, и сервер может это менять.
- **Поиск**: `pg_trgm` GIN по заголовкам, сообществам и никам (кириллица и
  регистр проверены). Когда перерастём — Meilisearch.

## 3. «Горячее»

```
hot = sign(s) · log10(1 + |s|) + (created_at − 2026-01-01) / 45000,   s = ups − downs
```

[`backend/internal/ranking/hot.go`](../backend/internal/ranking/hot.go) считает ранг
нового поста, SQL-функция `hot_rank()` с той же формулой — при сбросе голосов
воркером. Совпадение проверяется тестами.

- **Логарифм**: первые 10 голосов весят столько же, сколько следующие 90.
  Рано залетевший пост поднимается быстро, вирусный не висит вечно.
- **Время растёт, а не затухает**: свежесть входит как линейно растущая база, так
  что ранг меняется **только при голосовании**. Не нужен пересчёт по крону,
  индекс `(hot_rank, id)` стабилен. 45000 с = 12.5 ч: посту, который на 12.5 ч
  старше, нужно в 10 раз больше голосов.
- `1 + |s|` вместо Reddit-овского `max(|s|, 1)` — первый лайк тоже поднимает ранг.
- Отрицательный счёт топит пост симметрично.

С голосами ранги двигаются во время скролла: keyset по `(hot_rank, id)` может
пропустить пост, который взлетел выше курсора, или повторить опустившийся.
Клиент дедуплицирует по `id`. Пропуски лечит **снимок** (TODO): первая страница
фиксирует топ-500 id в Redis (`feedsnap:{uuid}`, TTL 30 мин), курсор = снимок +
смещение; глубже — обычный keyset.

Позже: нормализация по размеру сообщества для глобального «горячего» (чтобы
большие сообщества не забивали ленту), вес комментариев («обсуждаемое»).

## 4. iOS

### Что уже есть (каркас)

- `ios/Packages/VetkaKit` — локальный SPM-пакет, Swift 6 (strict concurrency),
  iOS 17. App-таргет — только `VetkaApp.swift`, всё остальное в пакете.
- **Core**: модели один-в-один с JSON бэкенда, декодер дат Go (RFC 3339 с дробью
  и без), `Route` + разбор deep links (`vetka://post/42`, `/c/`, `/u/`, `/comment/`).
- **Networking**: `Endpoint<Response>` (тип ответа задан запросом), `APIClient`
  (декодинг вне main, ошибки бэкенда → `APIError` с кодом), `API` — каталог
  эндпоинтов. На `token_expired` — один refresh и повтор запроса.
- **Session**: токены в Keychain, актор `TokenStore` (единственный refresh на все
  параллельные запросы, обновление за минуту до истечения, офлайн ≠ выход),
  `SessionStore` для UI.
- **DesignSystem**: токены цветов из [design-system.md](design-system.md)
  (`Palette`, светлая и тёмная палитры), отступы, пружины, haptics с
  прогретыми генераторами, skeleton с шиммером (уважает Reduce Motion),
  аватары-инициалы, «пилюли», основная кнопка, логотип, русские склонения.
  Где пара из handoff не дотягивала до WCAG, взят ближайший более тёмный
  оттенок того же тона: интерактивный зелёный `#119B82`, кнопки — белый на
  `#119B82` (в тёмной теме `#092B23` на `#20C997`), неактивные иконки
  `#68778A`, счёт голосов `#138660` / `#C64F56`; время — `text-secondary`.
- **AppFeature**: composition root без синглтонов, вкладки с отдельным
  `NavigationStack` на каждую, повторный тап по вкладке — к корню, deep links.
- **CommunitiesFeature**: вкладка «Поиск» (вкладки «Популярное» / «Подписки» со
  счётчиками, поиск; подписка и отписка в строке в одно касание) и страница сообщества
  (`CommunityScreen`): шапка на UIKit (аватар, название, кнопка подписки,
  описание, счётчики), вкладки «Лента» (new) / «Популярное» (hot) / «Правила».
  Заголовок появляется в навбаре, когда название шапки уезжает под него.
- **SearchFeature**: вкладка «Поиск» — поле в навбаре, фильтры, популярные
  запросы и «Недавние» (UserDefaults на аккаунт). Три запроса (сообщества,
  люди, посты) на каждый ввод разом, после паузы 300 мс: фильтр
  переключается без сети. Сообщества и посты кладутся в общие сторы.
- **FeedUI**: общая лента для вкладки «Лента», страниц сообществ и профилей —
  `FeedModel`/`FeedViewController` по `FeedSource` (`.all(sort)`,
  `.subscriptions`, `.community(slug, sort)`, `.user`), ячейки, раскладки и
  `HeaderPagerViewController`: шапка и вкладки лежат *поверх* страниц, а не
  внутри списков; страницы только поднимают верх safe area на высоту шапки,
  поэтому лента не знает, что у неё есть шапка. Касания мимо кнопок шапки
  проходят в список под ней (свайп с шапки скроллит). При смене вкладки
  шапка остаётся на месте: страница, прокрученная меньше высоты шапки,
  встаёт в ту же позицию, дальше — не трогается; короткой странице
  добавляется нижний отступ, чтобы шапку можно было спрятать.
- **Stores**: `PostStore` — identity map постов, общий для лент и экрана поста
  (голос или новый комментарий на экране поста уже в ленте при возврате);
  превью ленты не затирает полный текст. `VoteSync` — оптимистичные голоса
  (дебаунс, сверка, откат) для постов и комментариев. `CommunityStore`
  (`@Observable`, по slug в нижнем регистре) — сообщества и оптимистичная
  подписка: кнопка и счётчик меняются сразу, тапы склеиваются за 300 мс
  (двойной тап не шлёт ничего), PUT/DELETE состояния, ответ сверяет счётчик,
  ошибка — откат и haptic. Список не затирает загруженные правила. Вход или
  выход очищает стор — экраны перезагружают его с новым `is_subscribed`.
- **PostFeature**: пост и комментарии на одном `UICollectionView`; дерево —
  плоский список по `depth` с линиями веток, раскладки вне main. Поле ввода
  через `keyboardLayoutGuide`, оптимистичная отправка, сворачивание веток,
  «ещё N» на месте, экран ветки, строка истории.
- **ComposeFeature**: лист «+» на SwiftUI, черновик на устройстве (на аккаунт),
  настройки публикации (сообщество, история, 18+) отдельным листом. Текст —
  WYSIWYG на `UITextView`: смысл форматирования в атрибутах `.md*`, вид
  выводится из них, наружу (черновик, API) — markdown через `MarkdownCodec`.
  Формат markdown на сервере: `**жирный**`, `*курсив*`, `~~зачёркнутый~~`,
  `` `код` ``, `[текст](url)`, строки `## `, `> `, `- `; спецсимволы
  экранируются `\`. Рендер markdown в посте и ленте — TODO.
- **FeedFeature** (сама лента — в `FeedUI`): лента на `UICollectionView` (flow layout + diffable data
  source). Раскладка поста (`PostLayout`: кадры, тексты, высота) считается вне
  main при получении страницы и кэшируется по id и ширине; ячейки без Auto
  Layout только присваивают кадры. Горячее/Новое/Подписки — три контроллера в
  контейнере: переключение мгновенное, позиция скролла у каждой своя. Голоса
  оптимистичные: экран меняется сразу (haptic + пружина), тапы склеиваются за
  300 мс и уходят одним PUT с итоговым состоянием, ответ сверяет счёт, ошибка —
  откат. Скелетон вместо спиннера, догрузка за 10 постов до конца, дедуп по id.
  Голос без входа и «Подписки» без входа открывают шторку входа.
- Тесты: 86 в пакете (Swift Testing) + UI-смоук (вкладки, загрузка с бэкенда,
  back-swipe, deep link). Пакет: `xcodebuild test -scheme VetkaKit` в
  `ios/Packages/VetkaKit`.

### Модули (таргеты `VetkaKit`)

```
Features ──▶ Stores, DesignSystem, Media ──▶ Networking, Storage ──▶ Core
```

| Модуль | Что внутри |
|---|---|
| `Core` | модели, `Route`, логирование, утилиты |
| `Networking` | `APIClient` (async/await), `Endpoint`, refresh токена single-flight в actor, курсоры, `RealtimeClient` (WebSocket → `AsyncStream<Event>`) |
| `Storage` | GRDB (SQLite): нормализованный кэш постов/сообществ/юзеров и последних страниц лент; Keychain для токенов |
| `Media` | `ImagePipeline`, пул `AVPlayer` |
| `DesignSystem` | токены (цвета, шрифты, отступы), springs, `Haptics`, skeleton/shimmer, декодер ThumbHash |
| `Stores` | `PostStore` / `CommunityStore` — identity map; `VoteService` |
| `Feature*` | `Auth`, `Feed`, `Post`, `Comments`, `Community`, `Profile`, `Search`, `Compose` |

Фичи не зависят друг от друга: переходы только через `Route`. SPM-модули дают
быструю инкрементальную сборку и честные границы (`internal` по умолчанию).

### UIKit vs SwiftUI

- **Лента и комментарии — `UICollectionView`** (compositional layout + diffable
  data source + prefetching) с **чистыми UIKit-ячейками**. `LazyVStack`/`List`
  не дают контроля над reuse, prefetch и высотами, а `UIHostingConfiguration` на
  ячейку — лишняя работа layout'а на кадр. Высоты считаются заранее из данных
  (`width/height` медиа, размеры текста) вне main thread и кэшируются по `id + ширина`.
- Остальные экраны — SwiftUI, лента встраивается через `UIViewControllerRepresentable`.

### Навигация

`TabView` + `NavigationStack(path:)` на каждую вкладку; путь `[Route]` лежит в
`@Observable Router`. Deep links (`vetka://`, universal links) превращаются в
`Route`. Нативный navigation bar (кастомизируется через appearance) — так
interactive back-swipe никогда не ломается. Compose и авторизация — sheet,
просмотр медиа — кастомный UIKit-transition с zoom и swipe-down-to-dismiss.

### Сеть и потоки

- Swift 6 strict concurrency. `@MainActor` — только UI и stores. JSON-декодинг,
  парсинг markdown в `AttributedString`, расчёт высот — вне main thread.
- Access JWT (15 мин) + refresh с ротацией. Параллельные 401 ждут **один**
  refresh в actor.
- WebSocket: подписка на темы (`post:{id}` для открытого поста, счётчики видимых
  постов); события вливаются в stores, сервер шлёт их пачками раз в 1–2 с.

### Кэш и плавность

- **Изображения**: imgproxy отдаёт ширину из фиксированного набора (320/640/1080/1440)
  → меньше трафика и высокий cache hit. На клиенте: даунсэмплинг через ImageIO
  (`CGImageSourceCreateThumbnailAtIndex`) и предекодирование в фоне, `NSCache`
  готовых битмапов по `url + pixelSize`, сырые байты — в дисковом кэше,
  склейка одинаковых запросов, приоритеты и отмена. Пока картинка грузится,
  показывается ThumbHash.
- **Предзагрузка**: следующая страница — за ~10 ячеек до конца, картинки —
  на N ячеек вперёд, с отменой при уходе с экрана.
- **Холодный старт**: лента сразу из GRDB, затем фоновое обновление и применение
  diff (stale-while-revalidate). Skeleton только при пустом кэше.
- **Оптимистичный UI**: `VoteService` мгновенно меняет `PostStore` + haptic,
  частые тапы склеиваются (300 мс) и отправляется только итоговое состояние;
  при ошибке — откат с анимацией. Store один, поэтому лайк в деталях поста
  сразу виден и в ленте.
- **Видео**: в ленте — muted autoplay только для самой видимой ячейки, пул из 2–3
  `AVPlayer` вместо плеера на ячейку.

### Авторизация

- **Ник + пароль**: `POST /v1/auth/register` и `/v1/auth/login`. argon2id
  (OWASP: 19 MiB, 2 прохода) в отдельной таблице `password_credentials`.
  На неизвестный ник и неверный пароль — одинаковый `invalid_credentials`, и
  хеш считается в обоих случаях, чтобы по времени ответа нельзя было понять,
  есть ли аккаунт. Лимиты: 10 попыток на ник и 50 на адрес за 15 минут,
  10 регистраций в час с адреса. Регистрация сразу со своим ником — без
  онбординга.
- **Онбординг** (после входа через провайдера): выбор ника с живой проверкой
  `GET /v1/usernames/{name}/availability`, дебаунс 350 мс.
- **Локальная разработка**: вход по паролю работает без бота и без платного
  аккаунта Apple. Для Telegram есть `TELEGRAM_FAKE_LOGIN=true` — форма вместо
  виджета, сервер сам подписывает данные, дальше настоящий поток; с https в
  `PUBLIC_BASE_URL` сервер не стартует.

- **Sign in with Apple**: приложение генерирует случайный nonce и отдаёт Apple его
  SHA-256. Бэкенд проверяет `identityToken` по JWKS Apple (ключи кэшируются; если
  Apple лежит, работает устаревший кэш), а также `aud` = bundle ID и совпадение nonce.
- **Telegram**: `ASWebAuthenticationSession` открывает `/auth/telegram` (страница с
  Login Widget) → виджет редиректит на `/auth/telegram/callback` → тот пробрасывает
  параметры в `vetka://auth/telegram?...` → приложение шлёт их в
  `POST /v1/auth/telegram`. Подпись — HMAC-SHA256 ключом `SHA256(bot_token)`;
  повторное использование тех же данных блокируется через Redis `SET NX`.
  Нужен бот, к которому через @BotFather `/setdomain` привязан домен API
  (localhost не подходит — для локальной проверки нужен туннель).

## 5. Сессии

- **Access** — Ed25519 JWT на 15 минут, проверяется без похода в БД.
  Ed25519, а не HMAC: отдельный WebSocket-шлюз сможет проверять токены,
  имея только публичный ключ.
- **Refresh** — непрозрачный 128-битный токен на 60 дней, в БД хранится только
  SHA-256. Каждый `/refresh` выдаёт новый токен той же «семьи» (устройства).
- **Обнаружение кражи**: повтор уже обменянного токена позже чем через 30 с
  отзывает всю семью — и вор, и владелец входят заново. Повтор в пределах 30 с —
  это ретрай клиента после потерянного ответа, семья выживает.
- Коды ошибок задают поведение клиента: `token_expired` → тихий refresh и повтор
  запроса; `refresh_invalid` → выход на экран входа; `provider_unavailable` →
  «попробуйте ещё раз». Невалидный токен отклоняется даже на публичных
  маршрутах, чтобы клиент обновил его, а не смотрел ленту разлогиненным.
